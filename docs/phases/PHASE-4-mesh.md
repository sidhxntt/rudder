# Phase 4 — WireGuard mesh

**Target:** 2–3 weeks

**Demo:** an app connects to Postgres by hostname. The database has no public
port open.

The concepts here are simple. The debugging is not — **WireGuard failures are
silent.** Nothing errors, nothing logs, the packet just doesn't arrive. Budget
time for `tcpdump`, not for writing code.

---

## Prerequisites

- [ ] Phase 2 verified
- [ ] UDP 51820 reachable between all nodes
- [ ] Root or passwordless sudo for `wg`, `wg-quick`, `ip` on every node
- [ ] `wireguard-tools` installed
- [ ] If any node is behind NAT with no port forward, say so **before starting** —
      it changes the topology to hub-and-spoke and that's a different design

Strong suggestion: run this phase on cloud hosts, not local VMs. WireGuard bugs
that only appear over a real network with real latency and real MTU limits are
exactly the ones you want to hit.

---

## Steps

### 1. Key management

Keypair per node, generated on the node, public key sent to the control plane at
registration. **Private keys never leave the node.**

Per-service WireGuard IP allocated from the environment's `wg_subnet`. Allocation
must be transactional — two services allocating simultaneously must not receive
the same IP.

### 2. Peer config generation

Control plane renders `wg0.conf` per node. The agent applies it with:

```bash
wg syncconf wg0 <(wg-quick strip wg0.conf)
```

**Not `wg-quick down && wg-quick up`.** That drops every existing connection on
the node for the duration. `syncconf` applies the diff in place.

Regenerate and push on: service create, service destroy, service reschedule, node
join, node leave.

### 3. Service discovery

CoreDNS on each node. Zone file generated by the control plane.

`{service}.internal` → that service's WireGuard IP.

Regenerate on every event that changes a service's IP or location. A stale zone
file is the second most common silent failure in this phase.

Containers get the node's CoreDNS as their resolver.

### 4. Environment isolation

Different `wg_subnet` per environment. No route between them.

This must be verified, not assumed. Staging must not be able to reach production
even if someone hardcodes an IP.

### 5. Database services

`kind=database` services get **no Domain row and no Traefik router**. Reachable
only over the mesh.

This is a hard rule in the routing code, not a UI default someone can override.

## Where this goes wrong

**Silent peer failures.** A peer is missing from one node's config. That node
cannot reach that service. Nothing errors — packets are dropped, connections hang
until timeout. Symptom looks like an application bug.

Diagnostic order: `wg show` (is the peer there? recent handshake?) → `ping` the
wg IP → `tcpdump -i wg0` → only then look at the app.

**Key rotation.** Regenerating a node's keypair invalidates it in every other
node's config simultaneously. Sequence matters: distribute the new public key
everywhere first, then switch the node over.

**IP allocation races.** Two services created at once from the same subnet. Needs
a transaction or a unique constraint on `(environment_id, wg_ip)`.

**Stale DNS after reschedule.** Service moves from node A to node B, its wg IP
changes, the zone file is not regenerated. Every consumer resolves to a dead
address until TTL expiry — and CoreDNS defaults may cache longer than you expect.
Set a short TTL, and regenerate synchronously on reschedule.

**MTU.** WireGuard adds overhead. Default 1420 works over most links; over some
tunnels or cloud networks it does not, and the symptom is that small packets work
and large ones vanish. If TLS handshakes hang but ping works, it's MTU.

**Subnet exhaustion.** A `/24` per environment is 254 addresses. Fine. A `/28`
is not. Pick the allocation size deliberately and record it.

## Verify

```bash
# 1. Mesh is up, all peers handshaking
wg show          # on each node — recent handshake for every peer

# 2. Cross-node resolution and connectivity
docker exec <app-container> ping -c1 postgres.internal
docker exec <app-container> psql "$DATABASE_URL" -c 'select 1'

# 3. Database has no public port
docker inspect <postgres-container> | grep -A5 PortBindings
# → empty
nmap -p 5432 <node-public-ip>
# → closed or filtered

# 4. Environment isolation
docker exec <staging-app> ping -c1 <production-service-wg-ip>
# → 100% packet loss. Must fail.

# 5. Reschedule updates DNS
#    kill the node running postgres
#    → postgres.internal resolves to the new IP within 30s
docker exec <app-container> dig +short postgres.internal

# 6. syncconf does not drop traffic
#    hold an open connection, add a new service, confirm the connection survives
```

## Done when

- [ ] All nodes peer with all nodes, handshakes current
- [ ] `{service}.internal` resolves and connects across nodes
- [ ] Database services have no published ports and no Traefik router
- [ ] Staging provably cannot reach production, by IP or by name
- [ ] Rescheduling a service updates DNS within 30s
- [ ] Adding a service does not interrupt existing connections
- [ ] IP allocation race test passes
- [ ] Diagnostic runbook written — the `wg show` → `tcpdump` order above, in
      `../decisions/` or the README. You will need it again.
